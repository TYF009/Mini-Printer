# 03-软件设计 · 02 · 消息队列（环形打印缓冲）

## 1. 为什么需要队列

BLE 接收速度（毫秒级一包）与打印速度（一行几十毫秒）差一个量级，且 384×1000 的整幅图有 48KB 数据，**不能"收到就打、边收边同步打"**。解法：生产者-消费者模型——BLE 回调（生产者）把数据塞进环形缓冲，打印任务（消费者）按自己的节奏逐行取。

```
BLE onWrite ──写──> [环形缓冲 1000行×48B] ──读──> 打印任务逐行打印
              w_index 追加                 r_index 追赶
```

## 2. 数据结构（utils/em_queue.cpp）

```c
uint8_t printer_buffer[1000][48];   // 1000 行 × 48 字节（384点/8）
volatile int w_index, r_index;      // 写、读指针
volatile int left_line;             // 剩余未打印行数
SemaphoreHandle_t print_mutex;      // FreeRTOS 互斥锁
```

- **写**（`write_to_printbuffer`）：拷贝一行入 `w_index` 位置，`w_index = (w_index+1)%1000`，`left_line++`；缓冲满（left_line ≥ 1000）则丢弃——背压靠 App 侧控制发送节奏
- **读**（`read_one_line_data`）：取 `r_index` 行，`r_index` 前移，`left_line--`
- 环形语义：读写指针都在 0~999 循环，读过的行被新数据覆盖，**静态 48KB 内存支撑无限长的打印流**

## 3. 并发安全

写方（BLE 回调，跑在 BLE 协议栈任务）与读方（打印，跑在 loopTask）是不同任务——指针和 left_line 的读改写必须原子化，否则丢行/重行。每次读写都拿互斥锁；拿不到锁时**写入方选择放弃这一行而不是死等**（等待 10 tick 超时），宁可丢一行数据也不把 BLE 栈任务卡死（BLE 回调被阻塞会直接影响收包）。

## 4. 设计取舍

| 备选方案 | 放弃原因 |
|---|---|
| FreeRTOS 官方 Queue | 按元素拷贝、无"读指针回看"，不适合按行随机消费；且整块静态数组对内存布局更可控 |
| 流式（攒 100 行即开打） | 实际支持：编译开关 `START_PRINTER_WHEN_FINISH_RAED=0` 即为流式模式（缓冲够 100 行就开始打），当前整机配置采用"收完 A6 结束包再打"以保证任务完整性 |

已知缺陷（见 known-issues）：短包行尾残留旧数据、新任务开始未清队列、`clean_printbuffer()` 不持锁——修复记录见 04-项目整合。
